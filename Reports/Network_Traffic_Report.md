\# Network Traffic Analysis Report

\#\# 1\. Executive Summary

This project involved building a small virtualized network environment  
using Kali Linux and Ubuntu Server to practice network traffic capture  
and analysis.

The investigation focused on analyzing normal network communication,  
SSH traffic, and network reconnaissance activity generated by an Nmap  
TCP port scan.

Packet captures were collected using tcpdump and analyzed using  
Wireshark. The investigation demonstrated how network analysts can  
identify communicating hosts, determine protocols and ports, analyze  
TCP connection behavior, and recognize potential reconnaissance  
activity.

\# 4\. Investigation 1 — SSH Traffic Analysis

\#\# 4.1 Objective

The first investigation examined an SSH connection from Kali Linux  
to the Ubuntu Server.

The goal was to identify the hosts involved, the ports used, and  
how the SSH connection appeared within a packet capture.

\#\# 4.2 Connection Details

\*\*Source IP:\*\* 192.168.1.81    
\*\*Source Port:\*\* 58230

\*\*Destination IP:\*\* 192.168.1.245    
\*\*Destination Port:\*\* 22

\*\*Protocol:\*\* TCP    
\*\*Application:\*\* SSH

\#\# 4.3 TCP Three-Way Handshake

The connection began with the standard TCP three-way handshake:

    Kali → Ubuntu       SYN  
    Ubuntu → Kali       SYN/ACK  
    Kali → Ubuntu       ACK

The handshake demonstrated that a TCP connection was successfully  
established between the two systems.

\#\# 4.4 Encrypted Communication

After the TCP connection was established, additional traffic was  
observed between the two systems.

The packet capture showed information such as:

\- Source and destination IP addresses  
\- Source and destination ports  
\- Packet lengths  
\- TCP sequence and acknowledgment information  
\- Communication timing

However, the commands entered during the SSH session were not visible  
as readable plaintext.

This is expected because SSH encrypts the application data exchanged  
during the session.

\#\# 4.5 Assessment

The observed traffic was consistent with normal SSH communication  
between the Kali workstation and Ubuntu Server.

The investigation demonstrated that encrypted protocols can still  
expose useful network metadata while protecting the contents of the  
communication.

\# 5\. Investigation 2 — Nmap TCP Port Scan

\#\# 5.1 Objective

The second investigation analyzed network traffic generated by an  
Nmap TCP port scan against the Ubuntu Server.

The objective was to determine how port scanning appears in network  
traffic and how open and closed ports can be identified through  
packet-level analysis.

\#\# 5.2 Methodology

A packet capture was started using tcpdump before an Nmap scan was  
performed against the Ubuntu server.

The resulting capture was opened in Wireshark.

The following Wireshark filter was used to identify TCP SYN packets  
without the ACK flag:

    tcp.flags.syn \== 1 && tcp.flags.ack \== 0

This filter helped identify the TCP connection attempts generated  
during the scan.

\#\# 5.3 Observed Activity

The capture showed Kali sending TCP SYN requests to numerous  
destination ports on the Ubuntu server.

Examples included:

| Port | Nmap Result |  
|---:|---|  
| 22 | Open |  
| 80 | Closed |  
| 8888 | Closed |

This behavior showed one source host probing multiple ports on a  
single destination host.

\---

\#\# 5.4 Port 22 Analysis

The packet capture showed:

    38573 → 22 \[SYN\]  
    22 → 38573 \[SYN, ACK\]  
    38573 → 22 \[RST\]

The Ubuntu server responded to the initial SYN with a SYN/ACK,  
indicating that a service was listening on TCP port 22\.

Instead of completing the normal TCP handshake with an ACK, Kali  
sent a TCP reset.

This behavior is consistent with an Nmap TCP SYN/half-open scan.

Port 22 was identified as SSH.

\---

\#\# 5.5 Port 80 Analysis

Port 80 was reported as closed by Nmap.

The packet capture showed that the connection attempt did not result  
in a successful TCP connection. The Ubuntu server responded with a  
TCP reset, indicating that no service was accepting connections on  
that port.

\---

\#\# 5.6 Port 8888 Analysis

Port 8888 was also reported as closed by Nmap.

Similar to port 80, the packet capture showed that the connection  
attempt was rejected rather than establishing a TCP connection.

\# 6\. Security Findings

\#\#\# Finding 1 — SSH Service

TCP port 22 was accessible on the Ubuntu server and was running SSH.

\*\*Risk:\*\* SSH provides remote administrative access. If exposed to  
untrusted networks, weak credentials or vulnerable configurations  
could potentially be targeted.

\*\*Recommendation:\*\*

\- Use strong authentication.  
\- Disable unnecessary accounts.  
\- Keep the SSH service updated.  
\- Restrict SSH access to trusted hosts or networks when possible.  
\- Consider key-based authentication.

\#\#\# Finding 2 — Port Scanning Activity

The packet capture showed a single source host sending TCP SYN  
requests to numerous ports on the Ubuntu server.

This behavior is consistent with network reconnaissance.

\*\*Recommendation:\*\*

Network monitoring systems should identify unusual patterns of  
repeated connection attempts across many destination ports and  
generate alerts when appropriate.

\---

\# 7\. Indicators of Reconnaissance

The following characteristics were observed during the Nmap scan:

\- One source IP repeatedly communicated with one destination IP.  
\- Multiple destination ports were targeted.  
\- TCP SYN packets were repeatedly generated.  
\- Different TCP responses were used to determine port state.  
\- Port 22 responded with SYN/ACK.  
\- Closed ports responded with TCP reset packets.

These characteristics can help security analysts identify  
potential port-scanning activity within network traffic.
